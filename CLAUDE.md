# CLAUDE.md

Контекст проекта для Claude Code. Читать целиком перед изменениями.

---

## Что это за сервис

Коннектор **Efros Defense Operations (EDO)** — микросервис на Spring Boot, который
по команде извне забирает объекты защиты из EDO, отбирает нужные поля и отправляет
их в адаптер ePlat4m (e4) для импорта как Технические средства (ТС).

Язык: Java 21. Сборка: Maven. Упаковка: Docker.

---

## Место в общей подсистеме

В организации есть подсистема интеграции: набор коннекторов к внешним системам
(KSC, MaxPatrol, Efros CI, БДУ ФСТЭК и др.), которые тянут данные в продукт **САОБ**
на платформе **ePlat4m (e4)**, модуль **УКО**.

Стандартный поток в этой подсистеме:

```
Смежная система → Коннектор → RabbitMQ → Сервис агрегации → Сервис отправки → e4
```

**Наш коннектор идёт по упрощённому пути** — согласовано с тимлидом:

```
Efros DO → наш коннектор → (HTTP) → адаптер e4
```

Без RabbitMQ. Без Сервиса агрегации. Без собственной БД.
Агрегация не нужна, потому что EDO — единственный источник для этих данных,
склеивать не с чем.

## Кто нас запускает

**Менеджер задач (ТМ)** — оркестратор подсистемы. Планировщик: держит расписание,
дёргает сервисы, отслеживает статусы.

ТМ вызывает наш сервис по **фиксированному пути**, который он подставляет
в шаблон вместе с нашим адресом:

```
POST http://<наш адрес>/api/integration/launch
```

Путь задан документацией ТМ (раздел 1.5.1) — **произвольный путь придумать нельзя**.
Это единственный эндпоинт, который у нас есть (`IntegrationController`).

Тело запроса от ТМ:

```json
{"integration": {"taskGuid": "506ab972-...", "parameters": null}}
```

Ожидаемый ответ:

```json
{"accept": true, "condition": {"status": "running"}}
```

Мы обрабатываем задачу **синхронно** внутри этого же HTTP-запроса (логин → фильтр →
отправка в e4), затем отвечаем фиксированным ack. Дальнейших уведомлений об изменении
статуса не шлём — см. таблицу ниже.

## Что мы сознательно НЕ делаем

В документации ТМ описан большой контракт, но по решению команды мы реализуем
только его часть. **Не добавлять без явной просьбы:**

| Что | Почему не делаем |
|-----|------------------|
| Саморегистрация в ТМ при старте (`POST api/manage/regconn`) | Регистрируемся один раз вручную, см. `registration/` |
| `POST api/integration/interrupt` | Не требуется |
| `GET/PUT api/configuration` | Не требуется |
| `GET api/condition` | Не требуется |
| Уведомления `api/services/integration/condition` и `api/services/condition` | Решено не отправлять |
| RabbitMQ / Spring AMQP | Идём напрямую в e4 |
| Redis | Состояние между этапами не храним |
| Своя БД | Данные транзитные |
| Resilience4j / политики ретраев | Пока не требуется, добавим при необходимости |

Если задача выглядит так, что требует чего-то из этой таблицы — **сначала спросить**,
а не реализовывать по аналогии с документацией ТМ.

## Конфигурация

**В jar не зашито ни одного адреса и ни одного пароля.** `src/main/resources/application.yml`
содержит только порт, таймауты и уровень логов. Всё остальное задаёт тот, кто разворачивает
коннектор, тремя способами по возрастанию приоритета:

1. Значения по умолчанию внутри jar.
2. Внешний `config/application.yml` рядом с jar (в контейнере `/app/config/application.yml`) —
   Spring Boot подхватывает его сам, без флагов запуска. Шаблон: `config/application.yml.example`.
3. Переменные окружения — перекрывают файл. Имя выводится из имени настройки: верхний регистр,
   точки и дефисы в подчёркивания (`connector.edo.base-url` → `CONNECTOR_EDO_BASE_URL`).

Обязательный минимум — `base-url`, `login` и `password` и для `connector.edo`, и для `connector.e4`. `RequiredSettingsCheck` роняет контекст на старте с указанием недостающей
настройки, чтобы ошибка конфигурации не всплывала позже как 502 на первом запросе. Проверено
на собранном jar: без конфига падает с этим сообщением, внешний файл подхватывается,
переменная окружения перекрывает файл.

**Не возвращать реальные адреса и креды в `src/main/resources/application.yml`** — они уедут
в jar и в репозиторий. `config/application.yml` добавлен в `.gitignore`.

Логика намеренно линейная и плоская внутри каждого слоя. **Не плодить лишние
абстракции/интерфейсы там, где реализация одна** — читаемость важнее.

## Поток обработки

Внутри `IntegrationController.launch()` → `DeviceSyncService.run()`:

1. `edoClient.getSecurityObjects()` — `POST /api/v1/SecurityObject/GetListSoHierarchy`.
   Ответ — **дерево**: корневые группы, всё остальное вложено через `children` на любую
   глубину. Разворачивается в плоский список (`EdoSecurityObject.withDescendants`: родитель,
   затем его поддерево). Сам управляет токеном: если токена ещё нет,
   логинится (`POST /api/identity/Auth/LoginByPassword`); если EDO ответит 401 —
   сначала пробует `POST /api/identity/Auth/refreshToken/{refreshToken}`, и только
   если это тоже не сработало — логинится заново. Токен кешируется между вызовами:
   слать `LoginByPassword` на каждый прогон стенд не принимает.
2. Фильтр по полю `type == "SecurityObject"` (не `"Group"`) — `DeviceMapper`.
3. `host` объекта достаём из одного из трёх мест (по порядку): `host`, первый непустой
   `ciFeatures[].host`, первый непустой `acsFeatures[].host`.
4. Маппинг в `DeviceImport`.
5. `e4Client.importDevices(...)` — токен адаптера через `POST /api/getToken` (кешируется
   между прогонами), затем `POST /api/v1/import/Hardware` с `Authorization: Bearer`.
   Если адаптер ответит 401 — запрашивается новый токен и импорт повторяется один раз.

## Состав полей для импорта

Контракт согласован с тимлидом на реальном примере тела запроса (см. `DeviceImport.of`):

| Поле в e4 | Откуда | Комментарий |
|-----------|--------|-------------|
| `guid` | `id` | GUID объекта в EDO |
| `srcs.guid` | `id` | тот же GUID |
| `srcs.idAdjSys` | `id` | тот же GUID |
| `srcs.name` | — | константа `"Efros Defense Operation"` (без "s", в отличие от `regconn.json`) |
| `name` | `name` | Наименование |
| `purpose` | `description` | Описание |
| `ipv4` | `host` (3 источника, см. выше) | только если значение — IP-адрес |
| `hostName` | `host` (3 источника, см. выше) | если значение **не** IP-адрес (например, DNS-имя) |
| `sSourceInput`, `includedSys`, `storeInfA`, `swInstalled`, `sSoftwareInstances` | — | константа `"Нет"` |
| `loadConPhd` | — | константа `"Да"` |

Все три id-поля намеренно заполняются одним и тем же GUID из EDO: благодаря этому повторный
прогон обновляет запись в e4, а не создаёт дубль. **Не заменять на случайный UUID.**

`ipv4` и `hostName` — это один и тот же `host` из EDO, разложенный по двум полям: заполнено
не больше одного из двух. Поле `type` используется **только для фильтра**, в e4 не передаётся.

## Адаптер e4

Тестовый стенд: `https://10.10.18.174` — настоящий ePlat4m, не заглушка. Swagger у адаптера
не опубликован: на неизвестный путь сервер отдаёт `index.html` фронтенда с кодом 200.
Прод заказчика `10.10.37.142` — тоже ePlat4m (проверено по `<title>`), туда ничего не шлём.

В конфиге задаётся **базовый адрес** (`connector.e4.base-url`), пути — константы в `E4ApiPaths`.
Так же устроен конфиг соседнего ClassificationService: `address` плюс относительные пути.

### Авторизация — подтверждено на стенде

1. `POST /api/getToken`, тело `{"username": "DEV\\edo", "password": "..."}`.
   **Ключ именно `username` с маленькой `n`.** На `userName`, `login`, `user` и на пустое тело
   адаптер отвечает `500 {"error":"Value cannot be null. (Parameter 'value')"}`; на Basic — 400.
   Регистр закреплён тестом `E4TokenJsonTest`.
2. Ответ: `{"$type": "...TokenResultDto", "access_token": "eyJ...", "token_type": "bearer", "userName": "edo"}`.
   Refresh-токена нет — при 401 токен просто запрашивается заново (`E4TokenProvider.renew`).
3. `POST /api/v1/import/Hardware` с `Authorization: Bearer <access_token>` — на пустой массив
   стенд ответил `200 "Импорт завершен успешно"`.

Подсказку дал конфиг ClassificationService (`tokenAuthAdapterPath: api/getToken`).

### Почему у клиента e4 `BufferingClientHttpRequestFactory`

`SimpleClientHttpRequestFactory` шлёт тело chunked, без `Content-Length`. EDO это принимает,
а для адаптера подтверждён только запрос с `Content-Length` (так шлёт `curl`). Ошибка
`Value cannot be null` — ровно то, что .NET-бэкенд адаптера отдаёт, не найдя тела, поэтому
для e4 тело буферизуется и длина выставляется явно. Тело импорта — порядка мегабайта на
~1900 ТС, держать его в памяти не проблема. EDO-клиент не трогали — там chunked проверен.

### Остальное

- Тело импорта: массив `DeviceImport` (batch подтверждён тимлидом), все ТС одним запросом.
  Предел адаптера на размер тела не известен; `read-timeout` в шаблоне конфига — 120s.
- TLS: самоподписанный сертификат, e4-клиент доверяет ему так же, как EDO-клиент.
  **Для боевого контура это нужно пересмотреть.**
- Креды **не хранятся в репозитории**: внешний `config/application.yml` или переменные
  `CONNECTOR_E4_LOGIN` / `CONNECTOR_E4_PASSWORD`. Без них коннектор не стартует.

## Тестовые стенды EDO

- `https://10.116.41.37/` — сборка `2.52.2026.1012`.
- `https://10.116.48.160/` — сборка `2.52.2026.1011`.

Оба на самоподписанных сертификатах; оба клиента (EDO и e4) доверяют им через
`TrustAllRequestFactory`. Версия сборки — `GET /api/identity/App/info`.

**Swagger EDO разбит по сервисам.** UI — `/swagger/index.html`, выбор сервиса в списке
«Select a definition». JSON каждого сервиса лежит по `/swagger/docs/v1/<сервис>`, а не по
`swagger.json`: `identity` — логин, `so` — объекты защиты. Список методов сервиса одной строкой:

```
curl -k -s https://<стенд>/swagger/docs/v1/so | python3 -c 'import json,sys; d=json.load(sys.stdin); [print(m.upper(), p, "DEPRECATED" if o.get("deprecated") else "", "-", o.get("summary","")) for p,ops in d["paths"].items() for m,o in ops.items()]'
```

Используемые пути (подтверждены Swagger и вызовами на стенде):
- `POST /api/identity/Auth/LoginByPassword` — тело `{"userName": "...", "password": "..."}`.
- `POST /api/identity/Auth/refreshToken/{refreshToken}` — POST, подтверждено Swagger.
- `POST /api/v1/SecurityObject/GetListSoHierarchy` — пустое тело `{}`, ответ — дерево.

### Почему `GetListSoHierarchy`, а не `GetFlattenSoHierarchy`

У заказчика сертифицированная EDO `2.13.42.0.20260112.16`. `GetFlattenSoHierarchy` в ней,
по всей видимости, нет — это более новый метод. `GetListSoHierarchy` в свежей версии помечен
**DEPRECATED**, то есть существовал раньше и при этом ещё работает — один код подходит
и для нашего стенда, и для заказчика.

Сверено на стенде `10.116.41.37`: после разворачивания дерева оба метода дают одинаковые
числа — 1888 записей, 19 групп, 1869 ОЗ, из них 387 без `host` на верхнем уровне. Отличия
в полях: `ciFeatures` (массив) вместо `ciFeature` (объект), `parentSoId` вместо `parentId`
(не используем), плюс `children`.

**Риск:** вендор может убрать DEPRECATED-метод в следующих версиях. Тогда для новых версий
EDO придётся вернуться к `GetFlattenSoHierarchy` (плоский список, `ciFeature` — одним объектом).

## Реальная схема регистрации в ТМ (из /swagger/v1/swagger.json стенда)

Стенд ТМ (v1.1.7): `https://10.10.18.175:8443`, самоподписанный сертификат.
`regconn.json` сверен с реальной Swagger-схемой `RegistrationServiceData`, отличия от
первой версии (написанной по документации, не по факту):

- `identity.uId`, не `uid` (регистр).
- `condition.status` — enum с **Pascal-case** значениями: `None`/`Running`/`Free`/`Error`/`Stopped`
  (не `"free"` строчными).
- `currentConfig` — не произвольный объект, а сериализованный .NET `JsonDocument`:
  обязательная обёртка `{"isDisposable": false, "rootElement": {...наш конфиг...}}`.
  Содержимое `rootElement` при этом свободное (`additionalProperties: {}` в схеме).
- Верхнеуровневый `integration` — необязателен в `RegistrationServiceData`. Если задачи
  нет — блок просто не включаем в тело целиком (не шлём `{"taskGuid": null}` — там `taskGuid`
  обязателен и типа `string`/`guid`, `null` невалиден).
- Остальные эндпоинты ТМ (`GetListConn`, `GetStatus`, `DeleteConnector`, `StartConnector`)
  используют `{"limit": "..."}` / `{"serviceUId": "..."}` — как и было в `register.sh`, тут
  совпало с первого раза.

## Открытые вопросы (не выдумывать ответы — спрашивать)

1. **Маппинг адреса** — состав полей и batch подтверждены тимлидом, открыто:
   - если у объекта несколько `acsFeatures` с разными `host` — берём первый непустой, остальные теряем;
   - IPv6 в `host` уйдёт в `hostName`, а не в `ipv4` (регекс проверяет только IPv4);
   - если `host` нет нигде — оба поля (`ipv4`, `hostName`) уходят пустыми.
2. **`GetListSoHierarchy` в EDO 2.13.42** — у себя проверить нечем (наши стенды — 2.52).
   Нужен один вызов на площадке заказчика: метод есть, и форма ответа та же (дерево, `ciFeatures`).
3. **Несколько `ciFeatures` у одного ОЗ** — берём первый непустой `host`, как и для `acsFeatures`.
4. **`uId` сервиса для регистрации в ТМ** — сейчас `efrosdo_uko` по аналогии с
   `ksc_uko`/`maxpatrol_uko`. Само поле называется `uId` (подтверждено схемой), но
   принятый в команде формат значения (строка-слаг vs GUID) не подтверждён.
5. **`cronString`** для регистрации — сейчас `0 0 3 * * ?` (3 ночи), согласовать с тимлидом.
6. **Содержимое `rootElement` внутри `currentConfig`** — сейчас минимум (адреса), уточнить,
   нужно ли класть туда весь конфиг целиком (включая пароли, как в примере СА). Обёртка
   `JsonDocument` подтверждена схемой, содержимое — нет.

## Конвенции

- **Комментариев в коде нет** — решение команды. Смысл несут имена классов, методов
  и тестов; всё, что раньше было в комментариях, живёт здесь, в CLAUDE.md.
  Исключение — `config/application.yml.example`: это инструкция для того, кто разворачивает
  коннектор, там комментарии и есть содержание.
- **`// TODO` в коде не оставлять.** Открытые вопросы — только в разделе
  "Открытые вопросы" ниже.
- Логи и сообщения исключений — на русском, как принято в проекте.
- Java records для DTO; `@JsonIgnoreProperties(ignoreUnknown = true)` на DTO, куда
  маппится ответ внешней системы (реальные ответы EDO содержат больше полей, чем нам нужно).
- `RestClient` (Spring 6.1+), не `RestTemplate` и не `WebClient`.
- Таймауты (`connect-timeout`/`read-timeout`) настраиваются через `AppProperties`,
