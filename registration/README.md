# Разовая ручная регистрация в Менеджере задач

Наш сервис **не регистрируется сам**. Регистрация выполняется однократно вручную —
после этого ТМ помнит сервис в своей таблице `services` и начинает дёргать его по расписанию
через `POST /api/integration/launch` (см. корневой `CLAUDE.md`).

---

## Что нужно перед отправкой

1. **Адрес ТМ** — куда шлём. Например `http://10.10.10.10:80`.
2. **Наш адрес** — куда ТМ будет стучаться. Это `location.address` + `location.host` + `location.port`
   в `regconn.json`. Должен быть доступен из сети ТМ (не `localhost`) — подставить реальный адрес
   вместо плейсхолдера перед отправкой.
3. **Сервис должен быть уже развёрнут** по этому адресу. Регистрация не проверяет доступность
   сразу, но по расписанию ТМ придёт — и если нас нет, задача упадёт с ошибкой.
4. **Согласованный `uid`** — по нему ТМ ищет сервис. Менять потом больно: старая запись
   останется висеть, придётся удалять через `api/manage/deleteconnector`. Сейчас `efrosdo_uko`
   по аналогии с `ksc_uko`/`maxpatrol_uko` — формат не подтверждён тимлидом, см. TODO в CLAUDE.md.

## Шаг 1. Проверить, что ТМ жив, и посмотреть, кто уже зарегистрирован

```bash
TM=http://10.10.10.10:80

curl -s -X POST "$TM/api/performanceinfo/getlistconn" \
  -H "Content-Type: application/json" \
  -d '{"limit": "50"}' | jq
```

Показывает только сервисы с `isShadow = false`. Полезно, чтобы:
- убедиться, что ТМ отвечает;
- посмотреть, как выглядят uid у уже живущих коннекторов (`ksc_uko`, `maxpatrol_uko` и т.п.);
- проверить, что наш uid ещё не занят.

---

## Шаг 2. Отправить регистрацию

```bash
TM=http://10.10.10.10:80

curl -i -X POST "$TM/api/manage/regconn" \
  -H "Content-Type: application/json" \
  -d @regconn.json
```

Ожидаем `200`. Авторизация на эндпоинтах ТМ в документации не описана —
если прилетит `401`, спросить у владельца ТМ, какой заголовок нужен.

---

## Шаг 3. Проверить, что зарегистрировались

```bash
TM=http://10.10.10.10:80

curl -s -X POST "$TM/api/performanceinfo/getlistconn" \
  -H "Content-Type: application/json" \
  -d '{"limit": "50"}' | jq '.[] | select(.connectorUID == "efrosdo_uko")'

curl -s -X POST "$TM/api/performanceinfo/getstatus" \
  -H "Content-Type: application/json" \
  -d '{"serviceUId": "efrosdo_uko"}' | jq
```

## Шаг 4. Проверить запуск руками, не дожидаясь расписания

В регистрации `isManual: true`, поэтому задачу можно запустить с панели мониторинга
или запросом:

```bash
TM=http://10.10.10.10:80

curl -i -X POST "$TM/api/connector/startconnector" \
  -H "Content-Type: application/json" \
  -d '{"serviceUId": "efrosdo_uko"}'
```

## Если что-то пошло не так

### Удалить регистрацию и начать заново

```bash
TM=http://10.10.10.10:80

curl -i -X POST "$TM/api/manage/deleteconnector" \
  -H "Content-Type: application/json" \
  -d '{"serviceUId": "efrosdo_uko"}'
```

### Обновить только конфигурацию, не перерегистрируясь

```bash
curl -i -X POST "$TM/api/manage/setcurrentconfig" \
  -H "Content-Type: application/json" \
  -d @setcurrentconfig.json
```

Внимание: в этом запросе `currentConfig` передаётся **строкой** с экранированным JSON,
а не объектом (в отличие от `regconn`). Формат разный — не перепутать.

### Swagger у ТМ

ТМ поддерживает Swagger по адресу `/swagger/index.html`, но только если контейнер
запущен с `ASPNETCORE_ENVIRONMENT=Development`. Если у вас на стенде так —
это самый удобный способ отправить регистрацию и посмотреть точные схемы запросов.

## Повторная регистрация

По документации ТМ при получении `regconn` ищет запись по `uid`: если найдена — **обновляет**,
если нет — создаёт. То есть повторная отправка того же файла безопасна и работает как upsert.

Отдельно: если в сообщении есть `cronString`, ТМ создаёт или обновляет задачу расписания.
Если `cronString` убрать (`null`), существующие задачи расписания **удаляются**.
