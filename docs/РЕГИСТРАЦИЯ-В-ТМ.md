# Коннектор Efros DO — конфигурация для Менеджера задач

Версия 0.0.4

---

## 1. Как коннектор взаимодействует с ТМ

Менеджер задач вызывает сервис по фиксированному пути, который подставляет в шаблон вместе с адресом сервиса из регистрации:

```
POST http://<адрес из location.address>/api/integration/launch
```

Тело запроса:

```
{"integration": {"taskGuid": "506ab972-...", "parameters": null}}
```

Ответ:

```
{"accept": true, "condition": {"status": "running"}}
```

Это единственный эндпоинт, который предоставляет сервис. Задача выполняется синхронно внутри этого же HTTP-запроса: логин в EDO, выгрузка объектов защиты, фильтрация, маппинг, получение токена адаптера, отправка в адаптер e4. Ответ возвращается после завершения работы.

Если на любом шаге внешняя система вернула ошибку, коннектор отвечает кодом 502 с телом `{"message": "<описание>"}` вместо `accept`.

## 2. Таймаут ТМ на вызов коннектора

Из-за синхронной обработки ТМ держит соединение, пока идёт импорт. На тестовом стенде для 1869 ТС весь прогон занимает около 95 секунд, из них 91–97 секунд — обработка импорта адаптером.

**Таймаут ТМ на вызов коннектора нужно установить не меньше 180 секунд.** Стандартного для .NET значения в 100 секунд впритык хватает на 1869 ТС и не хватит при большем числе объектов. Если ТМ не дождётся ответа, он пометит задачу ошибкой, хотя импорт при этом пройдёт.

Для ориентира: таймаут ТМ должен быть больше таймаута коннектора на ответ адаптера (`connector.e4.read-timeout`, рекомендуется 120 секунд) плюс 10–20 секунд на работу с EDO.

## 3. Поведение, проверенное на стенде

Запуск через `POST /api/connector/startconnector` проверен на стенде ТМ v1.1.7:

- ТМ вызвал коннектор, передал `taskGuid`, дождался ответа и завершил задачу.
- Когда адаптер e4 был временно недоступен и коннектор вернул 502, ТМ **сам повторил запуск три раза с интервалом 20 секунд**; четвёртая попытка прошла успешно. При запуске по расписанию ТМ на ошибку делает пять повторов с тем же интервалом.
- Запуск по расписанию срабатывает: с расписанием «каждые 10 минут» ТМ вызывал коннектор в 07:10, 07:20 и 07:30. Повторный импорт безопасен: записи в e4 обновляются по GUID объекта EDO, а не создаются заново.
- Вызов `startconnector` возвращает ответ только после окончания работы коннектора, с учётом повторов — в описанном случае около 4 минут.

## 4. Что из контракта ТМ намеренно не реализовано

| Возможность ТМ | Статус |
|----------------|--------|
| Саморегистрация при старте (`POST api/manage/regconn`) | Не реализована — регистрируемся один раз вручную |
| `POST api/integration/interrupt` | Не реализована |
| `GET / PUT api/configuration` | Не реализована |
| `GET api/condition` | Не реализована |
| Уведомления `api/services/integration/condition` | Не отправляются |
| Уведомления `api/services/condition` | Не отправляются |

Следствие: после прогона ТМ продолжает показывать коннектор в состоянии `Running` — сообщить «свободен» некому. Если окажется, что ТМ не запускает по расписанию коннектор, числящийся в `Running`, уведомления о статусе придётся реализовать.

## 5. Состав регистрации

Тело запроса `POST /api/manage/regconn` — файл `regconn.json` в этом архиве. Схема сверена с реальным Swagger стенда ТМ версии 1.1.7 (`RegistrationServiceData`), а не с текстовой документацией — они расходятся.

**Адреса в `regconn.json` — тестового стенда. Перед регистрацией у себя заменить на свои.**

### 5.1. Блок identity — кто мы

| Поле | Значение | Комментарий |
|------|----------|-------------|
| `adjacentSystemType` | Efros Defense Operations | Тип смежной системы |
| `name` | Connector_EfrosDO_UKO | Техническое имя сервиса |
| `uId` | efrosdo_uko | Ключ, по которому ТМ находит сервис. По аналогии с ksc_uko, maxpatrol_uko |
| `alias` | Коннектор Efros Defense Operations (УКО) | Отображаемое имя |

Поле называется именно `uId`, с заглавной I — в текстовой документации указано `uid`, что схеме не соответствует.

Сменить `uId` после регистрации нельзя без удаления записи: ТМ ищет сервис по нему, и старая регистрация останется висеть. Удаляется через `POST api/manage/deleteconnector`.

### 5.2. Блок location — куда стучаться

| Поле | Значение на тестовом стенде |
|------|----------|
| `host` | 10.10.18.175 |
| `address` | http://10.10.18.175:8080 |
| `port` | 8080 |

Адрес должен быть доступен из сети ТМ. Именно сюда ТМ подставит путь `/api/integration/launch`.

### 5.3. Блок parameters — как запускать

| Поле | Значение | Комментарий |
|------|----------|-------------|
| `version` | 0.0.4 | Версия сервиса |
| `isManual` | true | Разрешён ручной запуск с панели мониторинга |
| `isShadow` | false | Сервис виден в списке getlistconn |
| `cronString` | 0 0 3 * * ? | Ежедневно в 03:00. Требует согласования |
| `flow.stages` | download, conversion, upload | Этапы обработки |
| `flow.upstream` и `flow.downstream` | пусто | Коннектор ни от кого не зависит: идёт в e4 напрямую, без Сервиса агрегации |

Если `cronString` передать как null, ТМ удалит существующие задачи расписания.

### 5.4. Блок currentConfig — конфигурация сервиса

По схеме это сериализованный .NET JsonDocument, поэтому обязательна обёртка:

```
"currentConfig": {
  "isDisposable": false,
  "rootElement": { ... }
}
```

Содержимое `rootElement` схемой не ограничено. Сейчас там адреса участников обмена — справочно, коннектор их отсюда не читает:

| Блок | Что описывает |
|------|---------------|
| `serviceSettings` | Имя, алиас и адрес самого коннектора |
| `adjacentSystemInteractionSettings.connectionSettings.address` | Адрес EDO |
| `adjacentSystemInteractionSettings.apiSettings.requestTimeout` | Таймаут запроса к EDO, 00:00:30 |
| `e4AdapterSettings.address` | Адрес адаптера ePlat4m |
| `taskManagerInteractionSettings.address` | Адрес самого ТМ |

Учётные данные в `currentConfig` не передаются: коннектор берёт их из собственного файла на хосте либо из переменных окружения.

Обновить конфигурацию, не перерегистрируя сервис, можно через `POST api/manage/setcurrentconfig`. Внимание: в этом запросе `currentConfig` передаётся строкой с экранированным JSON, а не объектом — формат отличается от regconn.

### 5.5. Блок condition

```
"condition": {"status": "Free"}
```

Значения статуса в схеме записаны в Pascal-case: None, Running, Free, Error, Stopped. Строчными («free») ТМ не примет.

## 6. Как отправить регистрацию

```
TM=https://10.10.18.175:8443

curl -k -i -X POST "$TM/api/manage/regconn" \
  -H "Content-Type: application/json" \
  -d @regconn.json
```

Повторная отправка безопасна: ТМ ищет запись по `uId` и обновляет её, если нашёл, то есть работает как upsert. Так же обновляется версия и `currentConfig` после выхода новой версии коннектора.

Проверить регистрацию и состояние:

```
curl -k -s -X POST "$TM/api/performanceinfo/getstatus" \
  -H "Content-Type: application/json" -d '{"serviceUId": "efrosdo_uko"}'
```

Запустить задачу вручную, не дожидаясь расписания (ответ придёт после окончания импорта):

```
curl -k -s -X POST "$TM/api/connector/startconnector" \
  -H "Content-Type: application/json" -d '{"serviceUId": "efrosdo_uko"}'
```

## 7. Что требует согласования

**Таймаут ТМ на вызов коннектора.** Решено сохранить синхронную обработку и увеличить таймаут на стороне ТМ — не меньше 180 секунд, см. раздел 2.

**Формат uId.** Сейчас `efrosdo_uko` — строка-слаг, по аналогии с соседними коннекторами. Принят ли в подсистеме именно такой формат, а не GUID, не подтверждено.

**Периодичность запуска.** Сейчас `0 0 3 * * ?` — ежедневно в три ночи. Значение выбрано произвольно, нужна реальная требуемая периодичность выгрузки.

**Статус Running после прогона.** Нужно убедиться, что ТМ запускает по расписанию коннектор, который у него числится в `Running`, — см. раздел 4.
